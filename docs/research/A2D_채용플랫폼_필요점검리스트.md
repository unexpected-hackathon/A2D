# A2D 채용 플랫폼 필요 점검리스트

2026년 10월 31일 · 김성원 담당 구현 범위 검토용

## 1. 목적과 적용 범위

이 문서는 「A2D 비침습 점검 및 위험 점수 설계」의 34개 항목 중 **소규모 채용·인재 매칭 플랫폼과 ATS 시연에 필요한 항목**을 추린다. 채용 플랫폼은 지원자 연락처·경력·학력·이력서 파일을 처리하고, `api`·`admin`·`staging`·외부 저장소 같은 접점이 함께 노출될 수 있다는 점을 기준으로 선정했다.

현재 공식 PRD의 시연 대상은 가상 여행 플랫폼이다. 이 문서는 채용 플랫폼 전환을 위한 우선순위 제안이며, 팀이 전환을 승인하기 전까지 PRD의 시연 대상과 수용 기준을 바꾸지 않는다.

아래 목록은 실제 기업을 공격하거나 침투하기 위한 목록이 아니다. A2D가 소유권을 확인한 가상 채용 플랫폼에서 읽기 전용으로 외부 노출을 확인하기 위한 구현 우선순위다.

## 2. 선정 원칙

1. 최근 채용 플랫폼 사고에서 반복된 **비인증 API, 지원자 파일, 클라우드 저장소, 관리·테스트 자산**을 우선한다.
2. 로그인 시도, 비밀번호 대입, 식별자 변경, 데이터 쓰기 없이 `GET`·`HEAD`·DNS 조회로 확인할 수 있어야 한다.
3. 자산의 존재와 취약점 확인을 구분한다. 관리자 화면이나 API 문서가 보인다는 사실만으로 침해 가능성을 확정하지 않는다.
4. 현재 PRD의 P0 흐름인 `발견 → 점수 → 오늘 할 일 → 조치 → 재점검 → 안전 점수 상승`을 먼저 완성한다.
5. PRD의 1차 29종 가운데 채용 사고와 직접 연결되는 항목을 먼저 구현하고, 나머지 P0 항목은 그 다음 순서로 구현한다.

## 6. 구현 순서

```text
1. 자산 범위       #1 → #4 → #5
2. 파일·비밀 노출  #8 → #9 → #11 → #12 → #14
3. API·관리 접점   #16 → #17 → #18 → #19 → (#34)
4. 기본 보안 상태  #23 → #28 → #30 → #31
5. 시연 검증       결함 조치 → 재점검 → 해결됨 표시 → 안전 점수 상승
```

현재 상세 설계의 계산 예시와 맞춰 시연의 첫 세 조치는 다음 순서를 기본으로 한다.

1. #16 비인증 지원자 API에 인증 적용
2. #8 공개 지원자 백업 제거
3. #18 관리자 페이지 접근 제한

#14 공개 지원자 파일 저장소가 시연 결함에 포함되면 #8과 비교해 안전 점수 상승 폭이 큰 항목을 코드가 먼저 고른다. LLM은 이 순서를 바꾸지 않는다.

## 7. 공통 안전 제한

- DNS TXT로 소유권을 확인한 도메인과 허용 목록 자산만 점검한다.
- HTTP 요청은 `GET`과 `HEAD`만 사용하고 쓰기·변경·삭제 요청을 보내지 않는다.
- 다른 등록 도메인으로 가는 리디렉션은 따라가지 않는다.
- 호스트당 초당 2건 이하, 점검당 HTTP 요청 300건 이하로 제한한다.
- 요청당 제한 시간은 10초, 점검 전체 제한 시간은 5분으로 둔다.
- 모든 요청에 A2D 점검임을 밝히는 User-Agent를 붙인다.
- 응답은 앞 512바이트까지만 저장하고 이메일·전화번호·키·파일 이름을 가린다.
- 모든 호출의 시각, 도구, 인자, 결과 요약, 거부 사유를 감사 기록에 남긴다.

## 8. 완료 기준

- 각 점검은 `정상`, `발견`, `확인 필요`, `실행 거부`, `오류` 중 하나로 끝난다.
- 발견에는 점검 번호, 자산 ID, 확실성, 가린 증거, 점수 요소가 저장된다.
- 관리자 페이지·API 문서·기술 식별처럼 존재만 확인한 결과를 침해로 표현하지 않는다.
- 시연 환경에 심은 우선 점검 결함을 모두 찾는다.
- 결함을 끈 뒤 재점검하면 해당 발견이 `해결됨`으로 바뀐다.
- 오늘 할 일 3가지를 조치한 뒤 조직 안전 점수가 상승하고 안전 등급이 F에서 D 이상으로 오른다.

## 9. 기존 문서와의 차이

기존 [도메인 선정 검증 문서](A2D_도메인선정_근거검증_사례28건.md)는 당시 설계를 기준으로 클라우드 저장소 검사를 미래 확장으로 분류했고, #34 백엔드 대행 서비스 점검은 아직 정의하지 않았다. 이후 현재 PRD와 상세 설계가 개정되어 #14와 새로 정의된 #34는 P0에 포함됐다. 구현 범위는 최신 PRD가 우선한다.

- #14의 제출 범위는 AWS S3와 네이버클라우드다. Google Cloud Storage와 Azure Blob Storage 지원은 범위 밖이다.
- #34의 제출 범위는 Supabase와 Firebase Realtime Database다. Firestore 지원은 범위 밖이다.
- 두 항목 모두 우리 사이트나 DNS가 직접 가리키거나 화면 코드에서 확인된 프로젝트만 검사하고 이름을 추측하지 않는다.
- 채용 시연 전환을 확정하면 `A2D_PRD.md`의 목표·페르소나·범위, `A2D_상세설계.md`의 발표 타깃·시연 결함, `target/README.md`의 가상 서비스 설명을 함께 변경해야 한다.
