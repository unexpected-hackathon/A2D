# A2D 주력 도메인 선정 및 프로젝트 적합성 검증

**의사결정 제안서 | 2026년 10월 31일 | A2D / Attack to Defense**

> **권고안: 소규모 채용·인재 매칭 웹서비스를 1차 대표 타깃으로 선정한다. A2D 핵심 점검 엔진은 업종 중립으로 유지하고, 채용 도메인은 첫 번째 검증 시나리오로 사용한다.**

**조사 범위** 2023-10-31 ~ 2026-10-31 (최근 3년) · 기존 사고 조사 엑셀 27건 + 추가 공식 사고 1건 = **총 28개 기록**. 이 수는 확인된 유출 28건을 뜻하지 않는다. 공개 노출, 연구 결과, 원인 미확정 사고, 공격자 주장도 포함된 **문헌 조사 목록**이다. 동일 사업자의 별도 사고는 구분하고, ApplyNow 파급 업체는 원사고와 중복 집계하지 않았다.

**기준 문서** 팀 제공 「A2D PRD」(2026-10-31), 「A2D 상세 설계」(10p), 기존 「최근 3년 유출·노출 사례 조사」 엑셀. 기술적 해석과 권고는 원문 사실과 구분해 기재한다.

## 1. 선정 결정 — 왜 채용·인재 매칭인가

### 1.1 고객 정의

- **핵심 고객:** 자체 웹사이트·API·지원자 파일을 운영하며 개발·서버 운영을 겸임하는 **보안 전담 인력이 부족한 소규모 채용 플랫폼·채용관리 SaaS(ATS)**.
- **대표 사용자:** 보안 비전문 IT 운영자 또는 개발자. 관리자·대표는 위험 점수와 조치 전후 변화를 이해하는 보조 사용자.
- **문제:** 지원자 개인이력·연락처·첨부 문서가 한 서비스에 모이지만, 도메인·API·테스트 서버·파일 저장소의 외부 접근 상태를 일관되게 확인하기 어렵다.
- **선정 방식:** 보안팀의 부재는 대상 고객을 정의한 **시장 가설**이다. 아래 대형 플랫폼 사고들이 곧 '소규모 기업에 보안팀이 없다'는 것을 증명하지는 않는다.

### 1.2 선택 근거를 4개의 질문으로 검증

|---|---|---|

### 1.3 제품 포지셔닝

**'채용 플랫폼 전용 취약점 공격기'가 아니라, '개인정보를 처리하는 소규모 웹서비스를 위한 AI 보조 외부 노출 점검기'**다. 채용 SaaS가 첫 번째 사례이며, 동일한 엔진을 교육·예약·커머스로 확장한다.

- **도메인 특화 영역:** 자산 중요도 기본값, 지원자 데이터 예시, 한국어 리포트, 표준 조치 가이드, 샌드박스 오류 구성.
- **범용 핵심 엔진:** DNS TXT 소유권 확인, D-01~D-05 자산 발견, C-01~C-17 점검 프레임워크, 위험 점수 산정, 증거 가림, 재점검·변경 추적.

**추가 독립 확인:** ApplyNow를 이용한 일본 지자체(우오누마시)는 자체 채용 지원 기록 86건과 담당자 등록정보 30건의 유출을 공식 공지했다. 이는 **동일 공급사 사고의 파급 사례**이므로 ApplyNow 사건과 별개 해킹으로 중복 계산하지 않는다. [지자체 공식 발표](https://www.city.uonuma.lg.jp/page/1044022.html)

**사건의 메시지:** 확인된 경로는 ① 웹 기능 인증·인가 미흡, ② 지원자 파일 저장소의 공개 설정, ③ 외부 도구·직원 계정의 침해로 분화된다. 이 중 **현재 MVP가 가장 직접적으로 대응하는 것은 ①의 일부인 '비인증 개인정보 API'**다. 다른 사례는 제품 확장 방향 또는 시장의 중요성을 보여주는 근거다.

## 3. A2D 기존 점검항목과의 적합성 매핑

아래 점검 ID와 P0/P1 구분은 팀의 「A2D 상세 설계」 및 「A2D PRD」를 따른다. **현재 가능한 검사**, **현행 검사로는 사실관계를 단정할 수 없는 경고**, **MVP 범위 밖의 확장**을 분리했다.

| 점검 ID | PRD 상태 | 채용 플랫폼 적용 | 판단 수준 / 구현 유의사항 |
|---|---|---|---|
| **D-01~D-05** 자산 발견 | P0 | `www`, `api`, `admin`, `staging` 등 소유권 확인 하위 자산과 문서·관리 경로 탐색 | 자산 존재 확인 ≠ 취약점. |
| **C-01** 백업 파일 | P0 | 허가된 웹 경로에 남은 지원자·이력서 백업 파일 | 공개 파일 형식까지 확인. S3/GCS/Azure 버킷 점검은 아님. |
| **C-02** 설정·소스 파일 | P0 | `.env`, `.git/HEAD` 등에 민감 설정 노출 | 증거 가림·원문 미보관. |
| **C-04** 로그·디버그 | P0 | 지원·접수 API의 디버그 출력·로그 흔적 | 오류 메시지의 보안 영향은 맥락 검토. |
| **C-05** 비인증 개인정보 API | P0 | 사전 승인된 테스트 지원자 조회 API에 **인증 없이 1회** 요청 | 결과에 개인정보 패턴 존재 ≠ 무조건 실서비스 정보 유출 확정. 보호 대상임을 검증해야 함. |
| **C-06** API 문서 공개 | P0 | Swagger/OpenAPI 노출 확인 | 공개 문서 자체가 항상 취약점은 아님. |
| **C-07** 관리 페이지 외부 노출 | P0 | 채용 운영 관리자 로그인 화면 발견 | 로그인 페이지 접근 ≠ 관리자 권한 탈취. |
| **C-09** TLS | P0 | 채용 서비스의 HTTPS 인증서·프로토콜 | 인증서 오류와 실제 데이터 유출을 구분. |
| **C-10** 보안 헤더 | P0 | 지원·로그인 화면의 헤더 점검 | 헤더 부재 ≠ 해당 공격 성공 입증. |
| **C-13** 알려진 취약 버전 | P0 | 식별된 서버·프레임워크 버전과 오프라인 취약 목록 대조 | 버전 추정만으로 악용 가능성을 확정하지 말 것. |
| **C-15** 잊힌 자산 | P0 | `dev`, `staging`, `old` 접점 발견 | 이름·외부 응답만으로 위험이 확정되지는 않음. |
| **C-16** 새 자산/노출 | P0 | 재점검에서 신규 지원 API·테스트 자산 변화 | 변경 기록·알림 후보. 최초 점검만으로 판단하지 않음. |
| **C-03,08,11,12,14,17** | 이번 MVP 제외 | 디렉터리 목록·평문 로그인·쿠키·CORS·EOL·메일 인증 | 상세 설계상 확장 점검 항목. |
| **미정의: Cloud Object Storage** | 미래 확장 | S3·GCS·Azure 버킷의 공개 접근 설정 검사 | **기존 C-01에 포함됐다고 주장 금지.** 저장소 소유권·허용 목록 별도 필요. |
| **미정의: BOLA/IDOR** | 미래 확장 | 권한 없는 지원자 간 비공개 프로필 조회 | 승인된 테스트 계정·데이터·접근 경계가 필요. 현재 로그인/식별자 조작 금지. |

### 탐지 가능성 판정 원칙

- **탐지 가능:** 승인된 가상 도메인/엔드포인트에서 허용된 GET·HEAD로 관찰 가능한 신호가 있고, 코드 판정 기준을 충족한다.
- **검토 필요:** 경로·화면의 외부 공개는 확인되나 '인가 누락' 또는 '데이터 유출'을 증명하지 못한다.
- **현재 불가:** 계정 탈취, 직원 PC 악성코드, IDOR/BOLA, 제3자 분석 도구, 클라우드 버킷 설정 등.

## 4. MVP 검증 시나리오와 PRD 변경안

### 4.1 시연 환경: 가상 채용·인재 매칭 플랫폼

기존 가상 여행 플랫폼을 **가상 채용 플랫폼**으로 교체할 것을 제안한다. 새 점검 엔진을 만들지 말고, 샌드박스의 서비스 명칭·테스트 엔드포인트·자산 중요도·조치 문장을 바꾼다. 실제 기업 도메인을 점검하지 않는다.

| 시연 순서 | 가상의 상태(심어 놓는 결함) | A2D 점검/조치 → 재점검 |
|---|---|---|
| ① | 지원자 조회용 **승인된 가상 API**가 비인증 요청에 더미 연락처 응답 | C-05가 발견·가린 증거 저장 → 인증 필수로 수정 → 해결됨 |
| ② | 가상 지원자 백업파일이 웹 공개 경로에 남아 있음 | C-01이 노출 확인 → 공개 경로에서 제거 → 해결됨 |
| ③ | 가상의 `.env` 설정 파일 형식이 외부 응답 | C-02가 확인 → 공개 차단 → 해결됨 |
| ④ | 테스트 채용 서비스/관리 로그인 경로가 외부 노출 | C-15/C-07 발견 → 관리자에게 추가 검토 권고 (접근만으로 침해 확정 아님) |
| ⑤ | 조치 전후 조직 위험도가 변경 | 코드 위험 점수·오늘 할 일 3가지 → FR-09 재점검 → FR-10 추이 표시 |

**A2D의 약속:** 코드가 증거를 수집·점수 계산·우선순위를 정하고, LLM은 승인된 도구만 호출해 설명한다. 소유권 확인 전 점검 금지, 허용하지 않은 목적지로 리디렉션 금지, GET·HEAD만, 호스트당 ≤2요청/초, 점검당 ≤300요청, 요청당 ≤10초, 5분 이내, 증거 최대 512바이트·개인정보 마스킹. 이는 최신 PRD의 FR-01~11, NFR-01~09와 동일하다.

## 5. 주 타깃 선택과 다른 업종으로의 확장

| 업종 | 개인정보의 성격 | 공통 EASM 재사용 | 별도 확인할 사항 |
|---|---|---|---|
| **채용·인재 매칭 (주 타깃)** | 이름·연락처·경력·학력·이력서 | 웹·API·관리 경로·백업·디버그·취약 버전 | 지원자 파일/권한 구조의 구체적 운영 방식 |
| 교육·학원 | 학생·보호자 정보, 상담·수강 | 공통 웹·API 점검 적용 가능 | 자체 시스템인지 외부 SaaS인지 |
| 중소 숙박·예약 | 예약자 정보, 일정·연락처 | 공통 웹·API 점검 적용 가능 | 예약 및 결제 시스템의 책임 범위 |
| 소형 커머스 | 주문·배송·고객정보 | 공통 웹·API 점검 적용 가능 | 호스팅 플랫폼이 운영하는 자산과 자체 자산 구분 |

**선택 논리:** '채용이 유일하게 보안 위험이 큰 업종'이 아니라 **지원자 데이터의 보호 가치, 확인된 외부 접점 사고, 안전한 샌드박스 재현 가능성, 범용 엔진 재사용**의 결합이 가장 설득력 있는 첫 번째 제품 이야기이기 때문이다. 이는 초기 제품 가설이지 통계적 시장 우위 입증은 아니다.

## 6. 결론과 팀 승인 요청

**최종 추천:** ① 주 고객은 소규모 채용·인재 매칭 서비스의 운영·개발 겸직자, ② 가상 채용 플랫폼에서 현재 P0 11종으로 발견→조치→재점검 시연, ③ 이력서 클라우드 저장소 공개·BOLA/IDOR는 사고 사례 기반 후속 로드맵, ④ 교육·예약·커머스는 공통 점검 엔진의 확장 영역으로 둔다.

**회의에서 확정할 4가지:**

1. 대표 업종/사용자 문구 확정과 PRD 반영 담당자.
2. 가상 여행 플랫폼을 채용 플랫폼으로 바꿀지, 변경 위험이 크면 여행 샌드박스를 유지하고 대표 시나리오만 채용형으로 시연할지 선택.
3. C-05 검증용 승인된 더미 API 및 백업/설정 파일 결함 목록 확정.
4. 제출 전 증거 수준, 오탐 0건, 조치 전후 점수 하락과 자료 출처 점검.

**제출 일정 주의:** 최신 PRD는 **2026-11-01 13:00 최종 커밋**을 기준으로 한다. 타깃 변경은 기존 P0 구현과 안전 제한을 깨지 않는 수준으로 결정해야 한다.
