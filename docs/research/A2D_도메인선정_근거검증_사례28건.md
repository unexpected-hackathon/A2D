# A2D 주력 도메인 선정 및 프로젝트 적합성 검증

**의사결정 기록 | 2026년 10월 31일 | A2D / Attack to Defense**

> **결정: 소규모 채용·인재 매칭 웹서비스를 A2D의 주 타깃으로 선정한다. 핵심 점검 엔진은 업종 중립으로 유지하고, 채용 도메인을 첫 번째 검증·시연 시나리오로 사용한다.**

> **갱신 (2026-10-31 저녁):** 주 타깃을 업종이 아니라 조직 조건인 **"보안 전담 인력 없이 웹·API로 개인정보를 다루는 소규모 조직"**으로 넓혔다. 해킹은 업종보다 노출된 취약점과 관리 인력 유무에 따라 일어나기 때문이다. 채용·인재 매칭 플랫폼은 **대표 사례이자 시연 도메인**으로 그대로 쓴다. 아래 문서의 "주 타깃"은 "대표 사례"로 읽는다. 최신 정의는 [기획서](../A2D_기획서.md)와 [PRD](../A2D_PRD.md)를 따른다.

> **갱신 (2026-11-01):** 핵심 타깃을 **"AI 코딩 도구와 BaaS로 개인정보를 다루는 서비스를 만들어 직접 운영하는 1~3명 팀"**으로 좁혔다. 결과를 받아 직접 고칠 수 있는 사람이어야 "방어를 누구나"가 성립하기 때문이다. 가상 채용 플랫폼은 이런 팀이 만든 서비스로 시연한다. 3막 이야기의 근거는 [문제 정의 근거 사례](A2D_문제정의_근거사례.md)에 있다.

**조사 범위** 2023-10-31 ~ 2026-10-31 (최근 3년) · 기존 사고 조사 엑셀 27건 + 추가 공식 사고 1건 = **총 28개 기록**. 이 수는 확인된 유출 28건을 뜻하지 않는다. 공개 노출, 연구 결과, 원인 미확정 사고, 공격자 주장도 포함된 **문헌 조사 목록**이다. 동일 사업자의 별도 사고는 구분하고, ApplyNow 파급 업체는 원사고와 중복 집계하지 않았다.

**기준 문서** 팀 제공 「A2D PRD」(2026-10-31), 「A2D 상세 설계」(10p), 기존 「최근 3년 유출·노출 사례 조사」 엑셀. 기술적 해석과 권고는 원문 사실과 구분해 기재한다.

## 1. 선정 결정 — 왜 채용·인재 매칭인가

### 1.1 고객 정의

- **핵심 고객:** 자체 웹사이트·API·지원자 파일을 운영하며 개발·서버 운영을 겸임하는 **보안 전담 인력이 부족한 소규모 채용 플랫폼·채용관리 SaaS(ATS)**.
- **대표 사용자:** 보안 비전문 IT 운영자 또는 개발자. 관리자·대표는 위험 점수와 조치 전후 변화를 이해하는 보조 사용자.
- **문제:** 지원자 개인이력·연락처·첨부 문서가 한 서비스에 모이지만, 도메인·API·테스트 서버·파일 저장소의 외부 접근 상태를 일관되게 확인하기 어렵다.
- **선정 방식:** 보안팀의 부재는 대상 고객을 정의한 **시장 가설**이다. 아래 대형 플랫폼 사고들이 곧 '소규모 기업에 보안팀이 없다'는 것을 증명하지는 않는다.

### 1.3 제품 포지셔닝

**'채용 플랫폼 전용 취약점 공격기'가 아니라, '개인정보를 처리하는 소규모 웹서비스를 위한 AI 보조 외부 노출 점검기'**다. 채용 SaaS가 첫 번째 사례이며, 동일한 엔진을 교육·예약·커머스로 확장한다.

- **도메인 특화 영역:** 자산 중요도 기본값, 지원자 데이터 예시, 한국어 리포트, 표준 조치 가이드, 샌드박스 오류 구성.
- **범용 핵심 엔진:** DNS TXT 소유권 확인, #1~#5 자산 찾기, #6~#34 점검 프레임워크, 위험·안전 점수 산정, 증거 마스킹, 재점검·변경 추적.

**추가 독립 확인:** ApplyNow를 이용한 일본 지자체(우오누마시)는 자체 채용 지원 기록 86건과 담당자 등록정보 30건의 유출을 공식 공지했다. 이는 **동일 공급사 사고의 파급 사례**이므로 ApplyNow 사건과 별개 해킹으로 중복 계산하지 않는다. [지자체 공식 발표](https://www.city.uonuma.lg.jp/page/1044022.html)

**사건의 메시지:** 확인된 경로는 ① 웹 기능 인증·인가 미흡, ② 지원자 파일 저장소의 공개 설정, ③ 외부 도구·직원 계정의 침해로 분화된다. 이 중 현재 MVP가 직접 대응하는 것은 **#16 비인증 개인정보 API, #8 공개 백업, #14 공개 저장소, #18 관리자 화면과 #19 테스트 자산 노출**이다. 계정 탈취와 외부 공급망 침해는 제품 확장 방향 또는 시장의 중요성을 보여주는 근거다.

## 3. A2D 점검항목과의 적합성 매핑

점검 번호와 P0 범위는 최신 [A2D 점검·점수 설계](../A2D_점검점수설계.md)와 [PRD](../A2D_PRD.md)를 따른다. 채용 플랫폼에서 먼저 구현할 목록과 전체 안전 조건은 [채용 플랫폼 필요 점검리스트](A2D_채용플랫폼_필요점검리스트.md)에 정리했다.

| 점검 번호 | PRD 상태 | 채용 플랫폼 적용 | 판단 수준 / 구현 유의사항 |
|---|---|---|---|
| **#1~#5, #24** 자산 찾기·식별 | P0 | `www`, `api`, `admin`, `staging`, 위탁 서비스와 기술 식별 | 자산 존재·제품 식별 자체는 취약점이 아니며 점수에 미반영. |
| **#8~#13** 파일·정보 노출 | P0 | 지원자 백업, `.env`·`.git`, 디버그 출력, JS 비밀키, 소스맵 | 원문과 키를 저장하지 않고 마스킹된 증거만 보관. |
| **#14** 클라우드 저장소 공개 | P0 | 이력서·증빙 파일 저장소 목록 공개 확인 | 우리 사이트·DNS가 직접 가리키는 AWS S3·네이버클라우드만, 목록 조회 1회. 파일 다운로드·쓰기 금지. |
| **#16** 비인증 개인정보 API | P0 | 승인된 더미 지원자 API에 인증 없이 1회 요청 | 개인정보 형태 존재와 실제 유출 사실을 구분. ID 변경·반복 조회 금지. |
| **#17~#21** API·관리 접점 | P0 | API 문서, 채용 관리자, 테스트 서버, 상태 페이지, CORS 확인 | 화면·문서 공개와 관리자 권한 탈취를 구분. CORS는 `가능성`으로 판정. |
| **#34** BaaS | P0 | 코드에 나타난 Supabase·Firebase Realtime DB의 공개 접근 확인 | 공개 키만 사용. 관리자 키 사용·쓰기·삭제 금지. Firestore는 범위 밖. |
| **#23, #25** 취약·지원 종료 버전 | P0 | 식별된 서버 버전을 오프라인 CVE·지원 종료 목록과 대조 | 버전 추정은 `가능성`이며 실제 악용을 확정하지 않음. |
| **#26~#28, #30~#31** 전송·브라우저 설정 | P0 | HTTPS, 인증서, 보안 헤더, 지원·로그인 쿠키 확인 | 설정 누락과 실제 공격 성공을 구분. |
| **#32~#33** 메일·도메인 | P0 | 채용 안내 메일의 SPF·DMARC와 운영 도메인 만료 확인 | 공개 DNS·RDAP만 조회. |
| **#7, #15, #22, #29** | 2차 | 열린 포트, 유출 계정, 보안 신고 창구, 오래된 TLS | 제출 버전에서 제외. |
| **BOLA/IDOR** | 미래 확장 | 권한 없는 지원자 간 비공개 프로필 조회 | 승인된 테스트 계정·데이터·접근 경계가 필요. 현재 로그인·식별자 조작 금지. |

### 탐지 가능성 판정 원칙

- **탐지 가능:** 승인된 가상 도메인/엔드포인트에서 허용된 GET·HEAD로 관찰 가능한 신호가 있고, 코드 판정 기준을 충족한다.
- **검토 필요:** 경로·화면의 외부 공개는 확인되나 '인가 누락' 또는 '데이터 유출'을 증명하지 못한다.
- **현재 불가:** 계정 탈취, 직원 PC 악성코드, IDOR/BOLA, 제3자 분석 도구 침해. 클라우드 저장소는 #14의 허용된 공급자와 소유권 범위 안에서만 가능하다.

## 4. MVP 검증 시나리오와 공식 반영 기준

### 4.1 시연 환경: 가상 채용·인재 매칭 플랫폼

가상 채용 플랫폼을 공식 시연 대상으로 사용한다. 새 점검 엔진을 만들지 않고, 업종 중립 엔진에 채용형 서비스 명칭·테스트 엔드포인트·자산 중요도·조치 문장을 적용한다. 실제 기업 도메인은 점검하지 않는다.

| 시연 순서 | 가상의 상태(심어 놓는 결함) | A2D 점검/조치 → 재점검 |
|---|---|---|
| ① | 지원자 조회용 **승인된 가상 API**가 비인증 요청에 더미 연락처 응답 | #16이 발견·마스킹된 증거 저장 → 인증 필수로 수정 → 해결됨 |
| ② | 가상 지원자 백업파일이 웹 공개 경로에 남아 있음 | #8이 노출 확인 → 공개 경로에서 제거 → 해결됨 |
| ③ | 가상의 이력서 저장소 목록 또는 `.env` 형식이 외부 응답 | #14 또는 #9가 확인 → 공개 차단 → 해결됨 |
| ④ | 테스트 채용 서비스/관리 로그인 경로가 외부 노출 | #19·#18 발견 → 관리자에게 추가 검토 권고 (접근만으로 침해 확정 아님) |
| ⑤ | 조치 전후 조직 안전 점수가 변경 | 코드가 안전 점수 상승 폭으로 오늘 할 일 3가지 선정 → FR-09 재점검 → FR-10 추이 표시 |

**A2D의 약속:** 코드가 증거를 수집·점수 계산·우선순위를 정하고, LLM은 승인된 도구만 호출해 설명한다. 소유권 확인 전 점검 금지, 허용하지 않은 목적지로 리디렉션 금지, GET·HEAD만, 호스트당 ≤2요청/초, 점검당 ≤300요청, 요청당 ≤10초, 5분 이내, 증거 최대 512바이트·개인정보 마스킹. 이는 최신 PRD의 FR-01~11, NFR-01~09와 동일하다.

## 5. 주 타깃 선택과 다른 업종으로의 확장

| 업종 | 개인정보의 성격 | 공통 EASM 재사용 | 별도 확인할 사항 |
|---|---|---|---|
| **채용·인재 매칭 (주 타깃)** | 이름·연락처·경력·학력·이력서 | 웹·API·관리 경로·백업·디버그·취약 버전 | 지원자 파일/권한 구조의 구체적 운영 방식 |
| 교육·학원 | 학생·보호자 정보, 상담·수강 | 공통 웹·API 점검 적용 가능 | 자체 시스템인지 외부 SaaS인지 |
| 중소 숙박·예약 | 예약자 정보, 일정·연락처 | 공통 웹·API 점검 적용 가능 | 예약 및 결제 시스템의 책임 범위 |
| 소형 커머스 | 주문·배송·고객정보 | 공통 웹·API 점검 적용 가능 | 호스팅 플랫폼이 운영하는 자산과 자체 자산 구분 |

**선택 논리:** '채용이 유일하게 보안 위험이 큰 업종'이 아니라 **지원자 데이터의 보호 가치, 확인된 외부 접점 사고, 안전한 샌드박스 재현 가능성, 범용 엔진 재사용**의 결합이 가장 설득력 있는 첫 번째 제품 이야기이기 때문이다. 이는 초기 제품 가설이지 통계적 시장 우위 입증은 아니다.

## 6. 결론과 확정 사항

**최종 결정:** ① 주 고객은 소규모 채용·인재 매칭 서비스의 운영·개발 겸직자, ② 가상 채용 플랫폼에서 P0 종단 흐름으로 발견→조치→재점검을 시연, ③ #14 이력서 저장소와 #34 BaaS 공개 접근은 P0, BOLA/IDOR는 후속 로드맵, ④ 교육·예약·커머스는 공통 점검 엔진의 확장 영역으로 둔다.

**구현·제출에서 확인할 4가지:**

1. PRD·기획서·상세 설계·시연 서버가 모두 채용 플랫폼을 주 타깃으로 표현하는지 확인.
2. #16 검증용 승인된 더미 지원자 API와 #8·#14 백업/저장소 결함 목록 확정.
3. 지원자 API·파일 저장소·관리자·테스트 서버의 자산 중요도와 표준 조치 시간 확정.
4. 제출 전 증거 수준, 오탐 0건, 조치 후 안전 점수 상승과 자료 출처 점검.

**제출 일정 주의:** 최신 PRD는 **2026-11-01 13:00 최종 커밋**을 기준으로 한다. 채용 도메인 반영은 업종 중립 점검 엔진과 기존 안전 제한을 유지하면서 시연 데이터·설명·우선순위를 바꾸는 수준으로 제한한다.
